Load this reference only when generalized case evidence or failure patterns will improve a decision. Universal mechanisms remain single-homed in references 01-07 and 09-11.

## How to Use Case Evidence

Treat each pattern as a bounded observation, not universal law. Extract the mechanism, load its canonical reference, and test whether the present system has the same conditions. Do not copy an earlier topology, interface, provider choice, or measurement into an unrelated design. A qualitative observation never becomes causal, repeatable, or portable evidence without a fresh necessity gate, acceptance plan, and domain-specific evaluation.

## Antipattern Catalogue

### Architecture before necessity

Building agents, bridges, interfaces, and persistence before proving that a direct or deterministic workflow is insufficient creates an expensive vehicle around the wrong bottleneck. Measure the simpler baseline first. Canonical mechanism: ref 01.

### Concatenation called lossless

Combining files without inventory, authority, conflict decisions, and reverse coverage may preserve bytes while destroying meaning. Use the distillation controls in ref 02.

### Agent amorphousness

An agent with a name but no unique inputs, tools, output contract, success checks, or boundary is a persona, not an architectural component. Canonical mechanism: ref 03.

### Process for every role

Turning each hat into a process multiplies latency, cost, context transfer, and failure surfaces before isolation proves useful. Canonical mechanism: refs 01 and 03.

### State inside the surface

Keeping the only run state in a chat or page loses continuity on navigation, restart, or carrier failure. Persistent product state belongs to ref 05; verifier evidence transport belongs to ref 10.

### `Executed` without readback

A tool or collaborator saying a change happened is an observed claim. Verify the target state, artifact, hash, test, or external system independently through ref 10.

### Structured fence without semantic payload

A JSON or YAML block may parse while meaningful lists are empty or truncated. Validate required semantic content and retention through refs 02 and 06.

### Generated report as decorated source

A report engine must select, interpret, structure, validate, and publish. Styling the wrong source is not report generation. Canonical mechanism: ref 06.

### Safety as product voice

Generic disclaimers can weaken usefulness while failing to enforce safety. Put safety in deterministic risk gates, tools, policy, and tests; keep reader warnings proportional. Canonical mechanism: ref 04.

### Canonical and archive mixed

When current doctrine, old drafts, and workshop notes load together, stale instructions can overrule the effective design. Separate canon, archive, runtime, and build evidence through refs 02 and 09.

## Packaging and Verification Lessons

### Duplicated mechanisms drift

When report contracts, secret patterns, version declarations, and root-resolution rules have multiple homes, they diverge. Give each mechanism one canonical owner and convert every known divergence into a deterministic gate.

### Tree fingerprints need executable recipes

A tree hash without path normalization, record format, encoding, exclusions, and an executable checker is not reproducible evidence. Bind release identity to a versioned manifest algorithm and independent readback.

### A running watcher may still miss evidence

Process liveness does not prove source observation. Recovery must reread the authoritative source, compare the physical maximum with the consumed checkpoint, expose connection loss, and rearm only from verified state. The universal mechanism belongs to ref 10.

### Public packages exclude private provenance

Originating case notes may guide authoring, but a public runtime package must contain only reusable doctrine, public source locators, neutral fixtures, and verifiable contracts. Private timelines, local paths, opaque identifiers, and personal receipts belong outside the runtime tree.
